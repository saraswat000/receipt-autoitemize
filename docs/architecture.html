Receipt upload, taxes and auto-itemize

Architecture and design review document

A Go HTTP service. A user uploads a receipt, and processing creates exactly one transaction with its tax lines as separate records, auto-itemized line items, the raw OCR text, and an itemize status (COMPLETE, NEEDS_REVIEW or FAILED). Users can edit, merge and split items. An edit that breaks the totals is rejected with 409 and the mismatch, and the service never invents a balancing line or adjusts a total.

OCR is stubbed, as the brief allows. No vendor is called and no API key exists. A text upload is its own OCR output, and an image or PDF named after a fixture returns that fixture's text. The engine sits behind an interface, so a real OCR or VLM engine drops in without touching the service.

API

EndpointBehaviour
POST /receiptsMultipart upload. File type is sniffed from the bytes (JPEG, PNG, WebP, GIF, PDF, text). Returns 201 and receipt_id, and flags identical bytes as duplicate_of.
POST /receipts/{id}/processOCR, extraction and auto-itemize. Creates or updates the one transaction. Sync by default (200); PROCESS_MODE=async answers 202.
GET /transactions/{id}Header, taxes, line items, itemize_status and issues. The version is exposed as the ETag.
POST /transactions/{id}/itemizeRe-runs auto-itemize from the stored OCR text. Replaces line items only; same transaction ID.
PATCH /transactions/{id}/itemsEdit, merge, split, add, delete, applied all-or-nothing. 409 with the numbers if the result does not reconcile; optional If-Match (412 when stale).
GET /receipts/{id}, GET /healthReceipt status (for async polling), OCR text and transaction link; liveness with a database ping.

Architecture

Dependencies point inward. The domain rules are pure functions, the service orchestrates use cases through interfaces, and infrastructure plugs in at the edges. cmd/server is the only place that knows which concrete pieces are used.

Why this shape

  • The service imports no infrastructure: no HTTP, SQL, os or worker package. Uploads go through FileStore, OCR engines receive bytes, and the pool is wired in cmd/server.
  • Interfaces live where they are used: api.Service, service.FileStore and service.Queue. The one exception is repository: two backends and the contract suite must import it without importing the service.
  • Domain rules are pure (no I/O, clock or IDs), so they are tested directly against gold.json.

Extension points

  • A real OCR/VLM engine implements ocr.Engine and inherits logging, caching and timeouts from the decorator chain.
  • Postgres is a new package that passes repotest.Run, plus one case in openRepository.
  • S3 is a second FileStore. A new PATCH op is a new command type and one registry entry; Apply does not change.

Data model

Taxes are rows, not a header number

A receipt can carry several rates (7% food and 19% drinks). inclusive separates "VAT 19%" added on top from "incl. VAT 19%" already inside the prices; without it the taxi fixture could never reconcile.

Exact types, enforced

Money is INTEGER cents; instants are epoch milliseconds (UTC); rates and quantities are exact decimals stored as a value and a power of ten (19.123% = (19123, 3)). Nothing is REAL, sums are overflow-checked, and tables are STRICT, so SQLite rejects a wrongly typed value.

Raw OCR is the source of truth

Every OCR run is kept. The transaction points at the run it was built from, so re-itemize is deterministic and re-processing keeps history.

Explainable status

itemize_issues carries the numbers behind NEEDS_REVIEW or FAILED (TOTAL_MISMATCH, SUBTOTAL_MISMATCH, NO_ITEMS, NO_TOTAL), so a review UI can say exactly what is wrong.

Reconciliation rule

sum(items) + sum(non-inclusive taxes) = grand_total, within one cent. Items are net of added tax, which matches gold.json. Tip and rounding lines count toward the total but are left out of the printed-subtotal check. A mismatch is reported, never fixed: the service does not change the total and does not invent a balancing line.

Processing flows

Process: sync (default) and async (PROCESS_MODE=async)

Async guarantees

  • The database is the durable queue; the channel is only a hand-off. A receipt is PROCESSING before it is queued, and on start every PROCESSING receipt is re-queued (snapshotted before the server accepts requests).
  • At-least-once, idempotent: the save is an upsert on receipt_id, so a job that runs twice still yields one transaction.
  • Bounded: OCR_WORKERS caps vendor concurrency; a full queue answers 503 and restores the receipt's previous state.

User edits (PATCH)

  • Operations run in order on a copy; the first invalid one aborts with 422 and nothing is written.
  • The result must reconcile with the stored total and taxes, or the answer is 409 with the issues and the proposed items.
  • The write is UPDATE … WHERE version = ?: a stale If-Match is 412, and a lost race without one is 409.
  • Re-itemize and PATCH replace items only; header and taxes never change.

What happens when things fail

FailureBehaviour
File has no readable textPermanent: receipt marked OCR_FAILED with a client-safe reason; 422 in sync mode. Never retried.
OCR times out or vendor errorsTransient. Sync: 504 OCR_TIMEOUT or 503 OCR_UNAVAILABLE, receipt unchanged so the client can retry. Async: retried with capped exponential backoff. Both modes share one Retryable rule.
Client disconnects mid-requestFailure records and status restores run with context.WithoutCancel, so they still happen.
A job panicsRecovered in the worker and recorded as a permanent failure with its stack, so a poison receipt cannot crash-loop the process.
Process crashes or shuts down mid-jobGraceful shutdown stops HTTP, then drains workers within a deadline (backoff sleeps are abandoned). Unfinished receipts stay PROCESSING and are re-queued on start.
Handler panicsMiddleware answers 500 in the standard error shape (unless the response has started) and the request is still access-logged; http.ErrAbortHandler propagates.
Internal error detailsNever sent to clients: ocr_error and error bodies carry client-safe messages; the full error is logged with the request ID.

Every log line of a request carries its request_id (a context-aware slog handler), including OCR decorator logs. Callers may send X-Request-ID; it is validated and echoed back.

Considered and left out: a state machine for receipt status (almost every transition is legal, since any receipt can be re-processed) and Specification objects for reconciliation (three short rules read better as one function).

S · O

Pure rules, orchestration, transport and storage are separate packages. New OCR engines, backends, file stores and PATCH ops are added, not edited in.

L · I

Both repositories are behaviourally identical (same contract suite). Small role interfaces: Receipts, OCRResults, Transactions, FileStore, Queue.

D

High-level policy depends on abstractions declared by the consumer; the composition root is the only place that names concrete types.

All tests run with the race detector. Beyond the test suite, the code was checked with staticcheck, govulncheck (no known vulnerabilities) and golangci-lint, and adversarially: bugs were only accepted when proven by a failing test, and each such test is kept as a regression test.

Adversarial testing

Four independent reviewers attacked concurrency, HTTP input, persistence and the domain rules. A bug only counted with a test that failed on the code. Examples of what was found and fixed:

AreaBug, now covered by a regression test
Reconciliation~185 maximum-size items made the int64 sum wrap onto the receipt total and save as COMPLETE; sums are now overflow-checked.
Extraction"Total VAT" lines were read as the grand total; "19% VAT" (rate first) and German payment lines were booked as items; tips could never reconcile; a UTF-8 BOM hid the merchant.
ConcurrencyA claim lease without a fencing token let a stale job run OCR again and overwrite a user's edits; the lease was removed (see tradeoffs).
PersistenceA torn read could pair version N with version N+1's items; the memory backend accepted a transaction-ID collision that SQLite refuses.
HTTPA 300-byte file extension caused a 500; unmatched routes answered plain text instead of the JSON error shape.

Choice for this scopeWhyProduction step
Stubbed OCR, regex parser over labelled textThe brief scores against fixtures; deterministic and testable.A VLM behind ocr.Engine returning structured JSON with per-field confidence; low confidence maps to NEEDS_REVIEW, and the reconcile rules stay as the guardrail on model output.
